# Frontend performance guardrails

Read before changing bundle baselines, shell rendering, or performance tooling.
Paths below are relative to `frontend/` except `.github/` and `docs/`.

## Ratchets and evidence (#2939)

- **Bundle gates** (`Lint / Frontend build`): Feature-PR growth per route must not exceed `max(10 KiB, round(base bytes × 0.02))` (`deltaTolerance` in `scripts/perf/bundle-policy.mjs`). A feature that needs more JS is allowed to grow: first check lazy loading (`next/dynamic`, `import()` on interaction) and lighter libraries; if the growth remains, set the PR label `bundle-growth-approved`, give the reason in the PR description and rerun the failed jobs (`gh run rerun <id> --failed`). The label turns delta failures into warnings for that PR only; it is read from the API on every run, so a rerun sees it. Absolute ceilings exist only for a few heavily used routes in `scripts/perf/bundle-ceilings.json` (framework floor `/_not-found`, portal logins and start pages, daily tenant pages), set generously above the measured state; the label does not waive them, raise one in the PR with a reason. Other routes, including new ones, need no policy entry. A ceiling crossing fails while the base keeps at least 1 KiB (`NEAR_CEILING_BYTES`) of headroom; a base already at or over it only warns on the PR (#5396). Development pushes, the nightly and release PRs into `main` have no base and check only the ceilings. A ceiling without a measured route fails, so a renamed route moves its entry.
- **Exact comparison**: `Lint / Frontend build` measures the tree it checked out: on pull requests GitHub's synthetic merge. Feature PRs compare it with the merge's first parent, the base tip it merges into, so the delta is exactly what the PR adds to its base and base drift since the merge-base cancels out; a checkout whose second parent is not the PR head fails. The merge compiles cold in every run. Its base parent compiles cold with the same Node/platform/environment and parser, from a disposable Git archive with its own frozen lockfile, removed even on failure; that measurement is then cached under the base's frontend source tree and build configuration (`measurementKey`) and reused by later runs of the same pull request, because two cold builds of one tree are byte-identical (#2939) and the cold build took 87–166 s per run. A restored file counts only as a valid measurement of exactly that identity; anything else is built cold again. A pull request reads only its own cache entries, so no other pull request or fork can supply one, and no token is passed to the base build. Missing requested measurements, malformed analysis or stale source/configuration fail closed. Both measurements and their base identity are archived for 14 days. There is no age-dependent lookup or fallback to historical approved references.
- **Workflow selection**: a `lint.yml`-only PR selects both frontend checks and the reusable `frontend-build` job through the `workflow-lint` filter; docs-only PRs still skip them. Source-contract tests evaluate the real workflow expressions for release, feature, stacked, nightly and lint-only contexts.
- **Policy ownership**: frontend maintainers review label approvals and ceiling changes in the PR. Observations never change policy. Shared client code is included in each affected route, not summed as a fictitious total bundle. The per-route budget files and their stale-reference ratchet (#5483) were removed in favour of the delta gate; [`docs/perf/bundle-ratchet-5483.md`](../perf/bundle-ratchet-5483.md) is history.
- **Local reproduction** (from `frontend/`, inside Devbox, with the normal local performance environment): commit frontend sources, then run `node scripts/perf/bundle-measurement.mjs --prepare-ci "$(git merge-base HEAD origin/development)"`, `node scripts/perf/bundle-measurement.mjs --build-base`, and `pnpm run perf:bundle-ratchet`. This is the same cold two-tree comparison as CI, of the head against its merge-base; CI compares the synthetic merge against the base tip, which a local merge of `origin/development` and `--prepare-ci HEAD^1` reproduces. Local results are platform-specific and must not replace Linux measurements. For release/nightly reproduction on the corresponding tested tree, run `node scripts/perf/bundle-measurement.mjs --prepare-ci` without a base and then `pnpm run perf:bundle-ratchet` without `--build-base`; this resets old delta metadata and checks the ceilings only. The extra base analysis/install is intentional: missing observations cannot silently disable the PR gate.
- **One cold build is analysis and regular build**: the ratchet runs `next build --analyze`, the regular production build (types, route validation, prerender) that also writes the Turbopack analysis data of `next experimental-analyze`; on next 16.4.5 both commands gave identical bytes on all 279 routes of one tree. No second build runs on the merge. Chunk splits depend on Turbopack's incremental cache, so the ratchet parks/restores that cache and compiles cold. `--skip-analyze` accepts only diagnostics matching the committed source/configuration. The base measurement keeps the cheaper `next experimental-analyze --output` (45 s against 127 s locally), since it needs only the analysis data. Release PRs stay on the merge tree; nightly/push use their checked-out revision. Versioned observations remain separate from the ceiling policy.

- **Render budget** (Vitest, blocking): `expectIdleRenderBudget` from `src/test/render-budget.tsx` counts `<Profiler>` commits over 5 s of fake-timer idle and caps them at 20; `mobile-bottom-nav.test.tsx` and `sidebar.test.tsx` use it. A new effect loop in the shell trips this regardless of runner speed. Keep the cap; fix the loop. Reuse the helper for any new always-mounted component.
- **Nightly counters** (`.github/workflows/perf-nightly.yml`, non-blocking): runs `pnpm run perf:trace` and `pnpm run perf:render` against a seeded backend on weeknights and via `workflow_dispatch`; the report lands in the job summary and as a 30-day artifact. Compare counters (requests per screen, duplicates, longest chain, renders per interaction) with `docs/perf/frontend-baseline-2026.md`; runner timings are not comparable across machines. Timing-based numbers (LCP, Lighthouse) are deliberately not gates.
